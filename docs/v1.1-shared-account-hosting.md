# v1.1 Shared Accounts and Hosting Plan

This is a post-submission v1.1 branch plan. It does not change the submitted release claim, its generated ZIP artifacts, or the fact that public hosting remains unvalidated until a real provider and staging checks pass.

## Central Account Model

One managed MariaDB database is the source of truth for `users` and their durable progress, favorites, ratings, activity, and canonical Community data. Existing foreign keys already bind those records to `users.id`; using the same account on another browser therefore reads the same central data. Guest progress remains browser-session-only until it is merged on successful sign-in.

`026_remembered_devices.sql` adds only persistent-browser authentication records. It is forward-only and leaves migrations `001` through `025` unchanged. A record stores a public selector and a hash of a random validator, never the raw validator. Successful automatic authentication rotates the validator. The account owner can revoke one browser or all remembered browsers; password reset/change revokes all remembered browsers.

## Provider-Neutral Hosting Requirements

Choose a managed PHP host and managed MariaDB service only when it provides PHP 8.2+, `mysqli`, HTTPS, a configurable document root, private writable storage, scheduled jobs, automated backups, restoration support, and host-managed environment secrets. Expose only `public/`; never expose the repository, artifact root, XAMPP, phpMyAdmin, a database port, `.env`, migrations, logs, backups, or private storage.

The runtime account uses least-privilege database credentials. Use a separate migration credential where the provider permits it. Inject `DB_*`, `APP_PRIVATE_PATH`, `APP_URL`, `REMEMBER_TOKEN_PEPPER`, and production cookie settings through the host secret mechanism or a private `.env` outside the web root. `REMEMBER_TOKEN_PEPPER` and `SESSION_COOKIE_SECURE=true` are mandatory in production. Do not trust proxy forwarding headers until an approved trusted-proxy configuration exists.

This v1.1 design intentionally supports one PHP application instance. Native PHP sessions and private file-backed rate limits are not suitable for horizontal scaling; move them to shared infrastructure before adding a second instance.

## Required Hosting Evidence Before Claiming Deployment

1. Select a provider and record PHP/MariaDB versions, secret injection, document root, and least-privilege account setup.
2. Validate HTTPS cookies, public-root denial, login/remembered-browser rotation, per-device revoke, logout-all, disabled-account rejection, and cross-browser central data on staging.
3. Rehearse managed-database backup restore and application rollback with a disposable copy before applying `026` to production.
4. Configure a scheduled cleanup of expired/revoked remembered-device records and document retention.
5. Run the full isolated test, migration, clean-package, and staging smoke matrices for the exact v1.1 commit.

Until all five are recorded, this branch makes no public deployment or managed-hosting readiness claim.
